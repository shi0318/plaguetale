## Step 1: Read the objective and distinguish the object
Open the current objective or journal information available in the game and compare it with the space in front of you. Identify whether the scene is asking for the sphere, another object, or a preceding interaction. A player can correctly remember a light-based mechanic while standing at a stage that has not yet enabled the expected action. Do not infer that every visible reflective surface must immediately display three selectable colors. Use prompts and state changes rather than a remembered screenshot alone.

Look around the accessible scene before repeating the same input. Check for an unfinished conversation, a visible interaction, or a route the objective still points toward. This is a method of reading the current puzzle, not a claim that one particular conversation universally unlocks the colors. Keep the distinction clear. If you find a missing preceding action and the scene changes afterward, you have useful progression evidence. If the scene offers nothing relevant, record that result and continue with the more focused checks below.

## Step 2: Test one input in the correct context
Inspect the current control assignment for the relevant tool or interaction. Use the action named by your installed game, especially if you changed bindings or switched between controller and keyboard. A guide's key label may not match your setup. Test one deliberate input while the scene is ready for it, then wait for the response. Rapidly cycling several commands can make it harder to tell whether the tool opened, closed, or never became available in the first place.

If the tool responds elsewhere but not in this scene, that is different from a binding that never works. ## Step 3: Observe light and feedback separately
Once the tool is active, watch for any change in illumination, a prompt, a sound, or a response from the relevant object. Different kinds of feedback answer different questions. A visual effect can show activation without proving that the intended receiver has been engaged. An interaction prompt can show availability without telling you the solution. Keep the comparison concrete: what changed, where it changed, and what the objective still asks. That is more useful than deciding the entire system is broken because the expected color display is absent.

Do not apply a universal red-blue-green sequence copied from an unrelated puzzle. The evidence used here does not verify a Chapter 5 combination or a fixed order that works everywhere. Instead, make a single reversible experiment when the interface permits one and observe the result before changing another variable. If you can identify a different state, compare it with the previous one. If nothing changes, stop repeating the same action after a clear comparison and retain the information for the checkpoint test.

## Step 4: Separate visibility from availability
Consider whether the expected interface is absent or merely difficult to see against the scene. Check the game's actual display and accessibility options without assuming a particular colorblind mode or contrast control exists. Read the available labels and compare one adjustment at a time if visibility is the problem. Keep your original settings recorded so you can reverse the test. This is not a claim that a graphics slider unlocks a puzzle mechanic; it helps distinguish a hard-to-read presentation from an unavailable action.

If other interface elements or effects are also missing, note that broader pattern. A rendering interruption affects more than one puzzle state, while a consistent absence in one interaction can be more local. Neither observation by itself diagnoses the cause. ## Step 5: Preserve progress during a checkpoint comparison
